# Fragility Report

I renamed the volatile `RequestTranscriptViewModel.body` field to `data` and updated its presenter, controller, HTTP adapter, and tests without changing the serialized response contents. I also extracted the interactor's model-response parsing helper into `ModelAnswerParser.parse`. The suite contained 12 tests and completed in 0.062 seconds after the refactor; 7 tests initially broke, all with `AttributeError` because they still referenced `.body`: 4 Testing-API-driven use-case tests and 3 presenter tests. The standalone fake-model tests (4) and the TestingApi seeding test (1) did not break, so the root cause was structural coupling to the view-model field name, not changed business behavior.

These results predict that a 1,000-test suite directly coupled to GUI or adapter structure would likely produce hundreds of similarly noisy failures for a small rename, because each test that reaches through the UI representation repeats the same implementation detail. A suite decoupled through a Testing API should keep most assertions on stable business responses and would be expected to retain nearly all of its tests, with failures limited to the small set that intentionally verifies the renamed adapter contract. The experiment therefore shows that the Testing API reduces refactoring cost by concentrating coupling at a narrow boundary rather than distributing it across the test suite.
